# DATA_MODEL - 나만의 여행 지도 (초안)

> 기준 문서: [IDEA.md](IDEA.md), [PRD.md](PRD.md), [TRD.md](TRD.md). 이 문서와 IDEA.md가 다르면 IDEA.md를 따른다.
> 범위: v0.1 ~ v1.0. DB 테이블은 v0.3부터 쓰지만, v0.1·v0.2의 메모리 저장도 같은 모양을 쓴다.

## 1. 한눈에 보기

- 테이블은 **`trips` 하나**다
- 다녀온 동네(v0.4)는 `trips` 안의 `dong_codes` 칸에 목록으로 넣는다. 처음부터 칸을 만들어 두고 v0.3까지는 빈 목록으로 둔다
- 지역과 동네의 이름, 모양, 넓이는 DB에 넣지 않는다. 지도 데이터 파일(`public/data/`)에서 코드로 찾는다
- 여행 번호처럼 TRD에서 "계산한다"고 정한 값은 저장하지 않는다 (5장)

### 테이블을 하나만 두는 이유
| 따로 만들 수 있는 테이블 | 만들지 않는 이유 |
|---|---|
| 지역 테이블 | 지역 이름·모양·넓이는 지도 데이터 파일에 이미 있다. DB에 또 넣으면 두 곳을 같이 고쳐야 한다 |
| 동네 테이블 | 위와 같다 |
| 여행-동네 연결 테이블 | 동네는 "이 여행에서 고른 목록"으로만 쓴다. 동네별로 모아 보는 기능이 PRD에 없어서, 여행 안의 목록 칸으로 충분하다 |

## 2. trips 테이블

여행 한 개가 한 줄이다.

| 필드 | 타입 | 제약조건 | 설명 |
|---|---|---|---|
| `id` | uuid | 기본 키, 자동 생성 | 여행을 구별하는 값 |
| `region_code` | varchar(5) | 필수, 숫자 5자리 | 여행한 시·군·구의 코드 (3장). 예: 대구 군위군 `27720`, 수원시 `41110` |
| `start_date` | date | 필수 | 시작일. 오늘까지만 (검사는 Zod에서, 아래 참고) |
| `end_date` | date | 비워 둘 수 있음. 값이 있으면 `start_date` 이상 | 종료일. 비어 있으면 당일치기 |
| `diary` | text | 필수, 기본값 빈 글자, 2,000자 이하 | 여행일기. 안 쓰면 빈 글자 |
| `dong_codes` | text[] | 필수, 기본값 빈 목록 | 다녀온 동네(행정동)의 코드 목록 (3장). v0.4부터 채운다 |
| `created_at` | timestamptz | 필수, 저장할 때 자동으로 현재 시각 | 기록한 시각. 시작일이 같은 여행끼리 번호와 목록 순서를 정할 때 쓴다. 수정해도 바뀌지 않는다 |
| `updated_at` | timestamptz | 필수, 저장할 때 자동으로 현재 시각 | 마지막으로 수정한 시각. 여행을 수정할 때마다 현재 시각으로 바뀐다 |

### 제약조건을 어디서 검사하는지
| 규칙 | DB | Zod (화면·서버) | 이유 |
|---|---|---|---|
| 필수 값, 숫자 5자리 지역 코드 | O | O | |
| 종료일 ≥ 시작일 | O | O | |
| 여행일기 2,000자 이하 | O | O | |
| 시작일은 오늘까지 | X | O | "오늘"은 날마다 바뀌어서 DB 규칙으로 두기 어렵다 |
| 동네 코드가 그 지역에 속하는지 | X | O | 지역 정보가 DB가 아니라 지도 데이터 파일에 있다 |
| 같은 동네를 두 번 고르지 않기 | X | O | 목록 칸 안의 중복은 DB 규칙으로 막기 번거롭다 |

### 필드에 대한 메모
- `diary`를 "비워 둘 수 있음"으로 하지 않고 기본값 빈 글자로 둔다. "없음"과 "빈 글자" 두 가지를 따로 처리하지 않기 위해서다
- `end_date`는 비워 둘 수 있게 둔다. "종료일 없음 = 당일치기"가 IDEA.md 규칙이기 때문이다
- 날짜는 시간 없이 날짜만(`date`) 저장한다. 시간대 때문에 하루가 밀리는 문제를 피하기 위해서다
- "시작일은 오늘까지"의 "오늘"은 한국 시간(Asia/Seoul) 기준이다. 서버가 다른 나라 시간으로 돌아가도 한국 날짜로 판단한다
- 여행을 수정하면 `updated_at`만 바뀌고 `created_at`은 그대로 둔다. `created_at`이 바뀌면 시작일이 같은 여행들의 번호와 순서가 달라지기 때문이다
- 여행을 삭제하면 그 줄을 DB에서 실제로 지운다. "지움" 표시만 남기지 않는다

## 3. 지역과 동네는 코드로 저장한다

### 결정
- 지역: **시·군·구 코드 5자리**를 저장한다. 지도 데이터의 `sgg` 값이다
- 동네: **행정동 코드 10자리**를 저장한다. 지도 데이터의 `adm_cd2` 값이다 (예: 대구 군위군 군위읍 `2772025000`)
- 이름은 저장하지 않고, 화면에 보여 줄 때 지도 데이터에서 코드로 찾는다

### 이유 1. 이름은 겹친다
2026-10-01판 지도 데이터에서 직접 확인했다.
- "중구"가 서울(`11140`), 부산(`26110`), 대구(`27110`), 대전(`30140`), 울산(`31110`)에 다 있다
- "신사동"이 서울 강남구와 서울 관악구에 둘 다 있다
- 코드는 겹치지 않는다. 행정동 3,559개의 `adm_cd2`가 모두 다른 것을 확인했다

### 이유 2. 지도 데이터가 바뀔 때 코드가 더 다루기 쉽다
이름도 코드도 바뀔 수 있다. 실제로 있었던 일이다.

| 바뀐 일 | 이름 | 코드 |
|---|---|---|
| 강원도 → 강원특별자치도 (2023, 확인 필요), 전라북도 → 전북특별자치도 (2024, 확인 필요) | 바뀜 | 앞 두 자리가 바뀜 (예: 강릉시 `51150`) |
| 부천시에 구가 다시 생김 (2024 확인 필요, 원미구·소사구·오정구) | 구 이름이 생김 | 구 코드가 생김 (`41192` 등) |
| 인천 중구·동구·서구 → 제물포구·영종구·서해구·검단구 (2026-07, 확인 필요) | 바뀜 | 바뀜. 경계도 바뀜 |
| 대구 달성군 구지면 → 구지읍 (2026-09) | 바뀜 | 새 코드 (`2771026800`) |
| 세종시 반곡동에서 현접동이 나뉨 (2026-07) | 새 이름이 생김 | 새 코드가 생김 |

- 이름은 바뀌어도 "바뀌었는지" 알기 어렵다. 같은 이름이 다른 곳에 있을 수 있기 때문이다
- 코드는 새 지도 데이터에 그 코드가 **없으면 바뀐 것**이라고 바로 알 수 있다
- 그래서 지도 데이터를 새 판으로 바꿀 때 아래 순서를 따른다
  1. DB에 저장된 코드 중 새 지도 데이터에 없는 코드를 찾는다
  2. 그 코드를 쓰는 여행을 목록으로 뽑는다
  3. 새 코드로 하나씩 바꾼다. 인천처럼 경계가 나뉜 경우는 직접 보고 고른다
- 지도 데이터는 TRD에서 정한 2026-10-01판으로 고정한다. 새 판으로 바꾸기 전에는 위 문제가 생기지 않는다
- v2.0 전에는 연습용 기록만 넣으므로, 바꾸기 어려우면 연습 기록을 지워도 된다

### 지도 데이터를 바꿀 때의 규칙
- 지도 데이터는 함부로 바꾸지 않는다
- 바꿀 때는 저장된 코드(지역, 동네)가 새 데이터에 모두 있는지 먼저 확인한다
- 없는 코드가 있으면 옛 코드 → 새 코드 변환표로 저장된 여행을 먼저 고치고, 그다음에 지도 데이터를 바꾼다

### 구가 있는 일반 시의 코드
- TRD 규칙에 따라 수원시 장안구 같은 구는 하나의 시로 합친다
- 구를 합칠지는 이름이 아니라 **코드로** 정한다
  - 시·도 코드가 특별시·광역시·세종(`11`, `26`~`31`, `36`)이 아닌 곳에서, 시·군·구 코드 끝자리가 `0`이 아니면 일반 시의 구로 본다
  - 예외: 증평군(`43745`), 태안군(`44825`)은 끝자리가 `0`이 아니지만 군이라서 합치지 않는다 (2026-10-01판 데이터에서 확인)
  - 특별시·광역시의 구도 끝자리가 `0`이 아닌 곳이 있어서(광진구 `11215`, 미추홀구 `28177` 등) 시·도 코드로 먼저 거른다
  - 지도 데이터를 바꿀 때 이 예외 목록이 맞는지 다시 확인한다
- 합친 시의 코드는 **구 코드의 앞 4자리 + `0`** 이다. 행정안전부가 시에 붙인 코드와 같다
  - 수원시: `41111`, `41113`, `41115`, `41117` → `41110`
  - 부천시: `41192`, `41194`, `41196` → `41190`
- 부천시처럼 구가 새로 생겨도 합친 시 코드(`41190`)는 그대로라서, 이미 저장된 여행을 고치지 않아도 된다
- 동네가 그 지역에 속하는지는 코드 목록 파일(TRD 6장)에 적힌 소속으로 확인한다. 코드 목록 파일을 만들 때 위 합치기 규칙으로 각 동네의 소속 시·군·구 코드를 정해 적어 둔다

## 4. TypeScript 타입 예시

`src/types/`에 둔다. DB 필드 이름은 `snake_case`, 코드 안에서는 `camelCase`로 쓴다.

```ts
// 시·군·구 코드 5자리 (예: "27720")
type RegionCode = string;
// 행정동 코드 10자리 (예: "2772025000")
type DongCode = string;
// 날짜 "YYYY-MM-DD" (예: "2026-10-28")
type DateString = string;

// DB에 저장된 여행 한 개
interface Trip {
  id: string;
  regionCode: RegionCode;
  startDate: DateString;
  endDate: DateString | null; // null이면 당일치기
  diary: string;              // 안 쓰면 ""
  dongCodes: DongCode[];      // v0.3까지는 []
  createdAt: string;          // 기록한 시각 (ISO 형식). 수정해도 그대로
  updatedAt: string;          // 마지막으로 수정한 시각 (ISO 형식)
}

// 새 여행을 만들 때 화면이 보내는 값 (id, createdAt, updatedAt은 서버가 정한다)
type NewTrip = Omit<Trip, "id" | "createdAt" | "updatedAt">;

// 화면에 보여 줄 때만 쓰는 모양. tripNumber는 계산해서 붙이고 저장하지 않는다
interface TripWithNumber extends Trip {
  tripNumber: number; // 1이면 "첫 번째 여행"
}
```

## 5. 저장하지 않는 값

TRD에서 계산하거나 지도 데이터에서 찾기로 한 값이다.

| 값 | 어디서 얻나 | 버전 |
|---|---|---|
| 여행 번호 | 계산 함수 (같은 지역의 여행을 시작일, 기록한 시각 순으로) | v0.1 |
| 목록 순서 (최신순) | 계산 함수 (목록 정렬) | v0.1 |
| 지역별 방문 횟수 | 계산 함수 (지역별 여행 개수) | v0.1 |
| 색칠 단계 | 계산 함수 (방문 횟수로) | v0.1 |
| 당일치기 여부 | `end_date`가 비어 있는지 보면 된다 | v0.1 |
| 지역 이름, 동네 이름 | 지도 데이터 파일 | v0.1 / v0.4 |
| 지역 넓이 | 지도 데이터 파일 (TRD 6장에서 미리 계산해 넣기로 함) | v0.4 |
| 지도 완성도 | 계산 함수 (가 본 지역 넓이 ÷ 전체 넓이) | v0.4 |

## 6. 정해야 할 것

- 지도 데이터를 새 판으로 바꾸는 시기. 바꿀 때는 3장의 순서를 따른다
