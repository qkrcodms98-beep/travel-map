# API_SPEC - 나만의 여행 지도 (초안)

> 기준 문서: [IDEA.md](IDEA.md), [PRD.md](PRD.md), [TRD.md](TRD.md), [DATA_MODEL.md](DATA_MODEL.md). 이 문서와 IDEA.md가 다르면 IDEA.md를 따른다.
> 범위: v0.2 ~ v1.0 (v0.1은 API 없이 화면 안에서만 동작한다). v0.2와 v0.3 이후는 저장 위치만 다르고 API는 같다.

## 1. 한눈에 보기

| 메서드 | 주소 | 하는 일 | 관련 기능 |
|---|---|---|---|
| GET | `/api/trips` | 여행 목록 가져오기 (전체 또는 한 지역) | F-02, F-04, F-07, F-08, F-13 |
| POST | `/api/trips` | 여행 추가 | F-03, F-11 |
| PUT | `/api/trips/{id}` | 여행 수정 | F-05, F-11 |
| DELETE | `/api/trips/{id}` | 여행 삭제 | F-06 |

### 엔드포인트를 4개로 줄인 이유
- **여행 하나만 가져오는 주소(GET `/api/trips/{id}`)는 만들지 않는다.** 여행 상세(F-04)에도 "두 번째 여행" 같은 번호가 필요한데, 번호는 같은 지역의 여행을 모두 알아야 계산할 수 있다. 그래서 상세 화면도 그 지역의 목록을 받아서 쓴다
- **지역·동네 목록을 주는 주소는 만들지 않는다.** 이름과 모양은 화면이 `public/data/`의 지도 데이터 파일에서 바로 읽는다
- **지도 색칠과 지도 완성도용 주소는 만들지 않는다.** 전체 여행 목록만 있으면 화면이 계산 함수로 구할 수 있다 (4장)

## 2. 공통 규칙

### 형식
- 요청과 응답은 JSON이다. 필드 이름은 camelCase다 (예: `startDate`)
- 날짜는 `"YYYY-MM-DD"` 글자다 (예: `"2026-05-03"`)
- 시각(`createdAt`, `updatedAt`)은 ISO 형식 글자다 (예: `"2026-05-05T09:12:30.000Z"`)
- 문서에 없는 필드를 보내면 에러로 처리한다 (`INVALID_REQUEST`). 오타 난 필드가 조용히 무시되는 것을 막기 위해서다

### 여행(Trip) JSON
DATA_MODEL.md의 `Trip` 타입과 같다.

```json
{
  "id": "6f1c2a4e-8b3d-4c2a-9f1e-2d7b5a9c0e11",
  "regionCode": "27720",
  "startDate": "2026-05-03",
  "endDate": "2026-05-04",
  "diary": "연습용 기록입니다.",
  "dongCodes": ["2772025000"],
  "createdAt": "2026-05-05T09:12:30.000Z",
  "updatedAt": "2026-05-05T09:12:30.000Z"
}
```

- `endDate`가 `null`이면 당일치기다
- `diary`를 안 썼으면 `""`이다
- `dongCodes`는 v0.4 전에는 항상 `[]`이다

### 에러 형식
모든 에러는 아래 모양 하나로 돌려준다.

```json
{
  "error": {
    "code": "END_DATE_BEFORE_START",
    "message": "종료일은 시작일보다 빠를 수 없어요."
  }
}
```

- `code`: 화면이 어떤 에러인지 구별할 때 쓰는 값. 바뀌지 않는다
- `message`: 사람이 읽는 한국어 안내 문구. 화면에 그대로 보여 줄 수 있다
- 한 번에 에러 하나만 돌려준다. 여러 규칙을 어기면 5장 검사 순서에서 먼저 걸린 것을 돌려준다

### 에러 코드 전체

| 코드 | 상태 코드 | 언제 | message 예시 |
|---|---|---|---|
| `INVALID_REQUEST` | 400 | JSON이 깨졌거나, 시작일이 아닌 다른 필드가 빠졌거나, 타입이 틀렸거나, 모르는 필드가 있을 때 | 요청 형식이 올바르지 않아요. |
| `START_DATE_REQUIRED` | 400 | `startDate`가 없거나, `null`이거나, 빈 글자일 때 | 시작일을 입력해 주세요. |
| `INVALID_DATE` | 400 | 날짜가 `YYYY-MM-DD` 형식이 아니거나 없는 날짜일 때 (예: `2026-02-30`) | 날짜 형식이 올바르지 않아요. |
| `START_DATE_IN_FUTURE` | 400 | 시작일이 오늘(한국 시간)보다 뒤일 때 | 시작일은 오늘까지만 고를 수 있어요. |
| `END_DATE_BEFORE_START` | 400 | 종료일이 시작일보다 빠를 때 | 종료일은 시작일보다 빠를 수 없어요. |
| `DIARY_TOO_LONG` | 400 | 여행일기가 2,000자를 넘을 때 | 여행일기는 2,000자까지 쓸 수 있어요. |
| `INVALID_REGION_CODE` | 400 | 지역 코드가 형식에 맞지 않거나 지도 데이터에 없을 때 | 지역을 찾을 수 없어요. |
| `INVALID_DONG_CODE` | 400 | 동네 코드가 형식에 맞지 않거나, 지도 데이터에 없거나, 그 지역의 동네가 아닐 때 | 동네 코드가 올바르지 않아요. |
| `DUPLICATE_DONG_CODE` | 400 | 같은 동네를 두 번 보냈을 때 | 같은 동네를 두 번 고를 수 없어요. |
| `TRIP_NOT_FOUND` | 404 | 그 `id`의 여행이 없을 때 (`id` 형식이 틀린 경우도 포함) | 여행을 찾을 수 없어요. |
| `INTERNAL_ERROR` | 500 | 서버나 DB에 예상하지 못한 문제가 생겼을 때 | 잠시 후 다시 시도해 주세요. |

- `INTERNAL_ERROR`의 `message`에는 DB 주소나 서버 내부 내용을 넣지 않는다

## 3. 엔드포인트

### 3-1. 여행 목록 가져오기 `GET /api/trips`

| 쿼리 | 필수 | 설명 |
|---|---|---|
| `regionCode` | 선택 | 넣으면 그 지역의 여행만, 빼면 전체 여행을 돌려준다 |

- 전체 목록: 첫 화면의 지도 색칠(F-08)과 지도 완성도(F-13)에 쓴다
- 지역 목록: 지역 화면(F-02)과 여행 상세(F-04)에 쓴다

**요청 예시**
```
GET /api/trips?regionCode=27720
```

**응답 예시** `200 OK`
```json
{
  "trips": [
    {
      "id": "6f1c2a4e-8b3d-4c2a-9f1e-2d7b5a9c0e11",
      "regionCode": "27720",
      "startDate": "2026-05-03",
      "endDate": "2026-05-04",
      "diary": "연습용 기록입니다.",
      "dongCodes": [],
      "createdAt": "2026-05-05T09:12:30.000Z",
      "updatedAt": "2026-05-05T09:12:30.000Z"
    }
  ]
}
```

- 여행이 없으면 `{ "trips": [] }`
- 목록 순서는 정해 두지 않는다. 화면이 목록 정렬 함수로 최신순으로 줄 세운다 (4장)

**에러**
| 상황 | 상태 코드 | 코드 |
|---|---|---|
| `regionCode`가 숫자 5자리가 아니거나 지도 데이터에 없음 | 400 | `INVALID_REGION_CODE` |
| 서버·DB 문제 | 500 | `INTERNAL_ERROR` |

### 3-2. 여행 추가 `POST /api/trips`

| 필드 | 필수 | 설명 |
|---|---|---|
| `regionCode` | 필수 | 시·군·구 코드 5자리 |
| `startDate` | 필수 | 시작일 |
| `endDate` | 선택 | 종료일. 빼거나 `null`이면 당일치기 |
| `diary` | 선택 | 여행일기. 빼면 `""` |
| `dongCodes` | 선택 | 동네 코드 목록. 빼면 `[]`. v0.4 전에는 `[]`만 받는다 |

**요청 예시**
```json
{
  "regionCode": "27720",
  "startDate": "2026-05-03",
  "endDate": "2026-05-04",
  "diary": "연습용 기록입니다.",
  "dongCodes": ["2772025000"]
}
```

**응답 예시** `201 Created`
```json
{
  "trip": {
    "id": "6f1c2a4e-8b3d-4c2a-9f1e-2d7b5a9c0e11",
    "regionCode": "27720",
    "startDate": "2026-05-03",
    "endDate": "2026-05-04",
    "diary": "연습용 기록입니다.",
    "dongCodes": ["2772025000"],
    "createdAt": "2026-05-05T09:12:30.000Z",
    "updatedAt": "2026-05-05T09:12:30.000Z"
  }
}
```

- `id`, `createdAt`, `updatedAt`은 서버가 정한다
- 저장한 뒤 화면은 `GET /api/trips?regionCode=...`로 목록을 다시 받아 번호를 계산한다

**에러**
| 상황 | 상태 코드 | 코드 |
|---|---|---|
| JSON이 깨짐, 타입이 틀림, 모르는 필드 | 400 | `INVALID_REQUEST` |
| 시작일이 없거나, `null`이거나, 빈 글자 | 400 | `START_DATE_REQUIRED` |
| 날짜 형식이 틀림 | 400 | `INVALID_DATE` |
| 시작일이 미래 | 400 | `START_DATE_IN_FUTURE` |
| 종료일이 시작일보다 빠름 | 400 | `END_DATE_BEFORE_START` |
| 여행일기가 2,000자 초과 | 400 | `DIARY_TOO_LONG` |
| 지역 코드가 틀림 | 400 | `INVALID_REGION_CODE` |
| 동네 코드가 틀리거나 그 지역 동네가 아님 | 400 | `INVALID_DONG_CODE` |
| 같은 동네가 두 번 | 400 | `DUPLICATE_DONG_CODE` |
| 서버·DB 문제 | 500 | `INTERNAL_ERROR` |

**에러 응답 예시** `400 Bad Request`
```json
{
  "error": {
    "code": "START_DATE_IN_FUTURE",
    "message": "시작일은 오늘까지만 고를 수 있어요."
  }
}
```

### 3-3. 여행 수정 `PUT /api/trips/{id}`

고칠 수 있는 값은 IDEA.md대로 날짜, 여행일기, 동네다. **지역은 고칠 수 없다** (`regionCode`를 보내면 `INVALID_REQUEST`).

| 필드 | 필수 | 설명 |
|---|---|---|
| `startDate` | 필수 | 시작일 |
| `endDate` | 필수 | 종료일. 당일치기면 `null` |
| `diary` | 필수 | 여행일기. 없으면 `""` |
| `dongCodes` | 필수 | 동네 코드 목록. 없으면 `[]` |

- 추가와 달리 4개 필드를 모두 보내야 한다. 하나를 빼먹었을 때 일기나 동네가 몰래 지워지는 것을 막기 위해서다
- 그 `id`의 여행이 없으면 내용 검사보다 먼저 `404 TRIP_NOT_FOUND`를 돌려준다

**요청 예시**
```
PUT /api/trips/6f1c2a4e-8b3d-4c2a-9f1e-2d7b5a9c0e11
```
```json
{
  "startDate": "2026-05-02",
  "endDate": null,
  "diary": "날짜를 고친 연습용 기록입니다.",
  "dongCodes": []
}
```

**응답 예시** `200 OK`
```json
{
  "trip": {
    "id": "6f1c2a4e-8b3d-4c2a-9f1e-2d7b5a9c0e11",
    "regionCode": "27720",
    "startDate": "2026-05-02",
    "endDate": null,
    "diary": "날짜를 고친 연습용 기록입니다.",
    "dongCodes": [],
    "createdAt": "2026-05-05T09:12:30.000Z",
    "updatedAt": "2026-05-06T14:00:00.000Z"
  }
}
```

- `updatedAt`만 바뀌고 `createdAt`은 그대로다 (DATA_MODEL.md)

**에러**
| 상황 | 상태 코드 | 코드 |
|---|---|---|
| 그 `id`의 여행이 없음 (내용 검사보다 먼저) | 404 | `TRIP_NOT_FOUND` |
| JSON이 깨짐, 시작일이 아닌 다른 필드가 빠짐, `regionCode`를 보냄 | 400 | `INVALID_REQUEST` |
| 날짜·일기·동네 규칙 위반 | 400 | 3-2와 같음 |
| 서버·DB 문제 | 500 | `INTERNAL_ERROR` |

### 3-4. 여행 삭제 `DELETE /api/trips/{id}`

**요청 예시**
```
DELETE /api/trips/6f1c2a4e-8b3d-4c2a-9f1e-2d7b5a9c0e11
```

**응답** `204 No Content` (본문 없음)

- 줄을 DB에서 실제로 지운다 (DATA_MODEL.md)
- "정말 지울까요?" 확인(F-06)은 화면에서 한다. API는 확인 없이 바로 지운다

**에러**
| 상황 | 상태 코드 | 코드 |
|---|---|---|
| 그 `id`의 여행이 없음 (이미 지운 경우 포함) | 404 | `TRIP_NOT_FOUND` |
| 서버·DB 문제 | 500 | `INTERNAL_ERROR` |

## 4. 계산하는 값은 응답에 넣지 않는다

### 결정
여행 번호, 목록 순서(최신순), 방문 횟수, 색칠 단계, 지도 완성도는 **응답에 넣지 않고 화면에서 계산한다**.

### 이유
- v0.1은 서버 없이 화면만으로 동작하므로, 화면에 이미 계산 함수가 있다. 서버가 또 계산하면 같은 일을 두 곳에서 하게 된다
- 계산 함수는 `src/lib/`에 하나만 두고 테스트한다 (CLAUDE.md). 화면이 그 함수를 쓰면 v0.1~v1.0 내내 같은 코드를 쓴다
- 지도 색칠과 완성도는 전체 여행 목록만 있으면 구할 수 있어서, 따로 주소를 만들 필요가 없다
- 응답이 DATA_MODEL.md의 `Trip`과 같은 모양이라 이해하기 쉽다

## 5. 서버 검사

### 입력 규칙 검사
화면에서도 Zod로 검사하지만, 서버도 **같은 Zod 규칙**으로 한 번 더 검사한다 (TRD 4장). 화면 검사를 건너뛰고 들어온 값을 막기 위해서다.

검사 순서 (먼저 걸린 에러 하나만 돌려준다)

| 순서 | 검사 | 에러 코드 |
|---|---|---|
| 0 | (수정할 때만) 그 `id`의 여행이 있는지 | `TRIP_NOT_FOUND` |
| 1 | JSON 모양, 시작일이 아닌 다른 필드가 있는지, 필드 타입, 모르는 필드 | `INVALID_REQUEST` |
| 2 | 시작일이 있는지 (없음, `null`, 빈 글자는 모두 여기서 걸린다) | `START_DATE_REQUIRED` |
| 3 | 날짜가 `YYYY-MM-DD` 형식이고 실제 있는 날짜인지 | `INVALID_DATE` |
| 4 | 시작일 ≤ 오늘 (한국 시간) | `START_DATE_IN_FUTURE` |
| 5 | 종료일이 있으면 종료일 ≥ 시작일 (같은 날은 괜찮음) | `END_DATE_BEFORE_START` |
| 6 | 여행일기 2,000자 이하 | `DIARY_TOO_LONG` |
| 7 | 지역 코드 (추가할 때만) | `INVALID_REGION_CODE` |
| 8 | 동네 코드 | `INVALID_DONG_CODE`, `DUPLICATE_DONG_CODE` |

- **"오늘"은 한국 시간(Asia/Seoul) 기준**이다. 서버가 다른 나라 시간으로 돌아가도, 요청을 받은 순간의 한국 날짜와 비교한다. 예: 한국 시간 2026-10-29 00:30에는 시작일 `2026-10-29`를 받는다
- **종료일은 미래여도 된다.** 예: 오늘 시작해서 내일 끝나는 여행. IDEA.md는 시작일만 오늘까지로 제한한다
- **글자 수는 화면과 서버, DB가 같은 방법으로 센다.** 이모지가 2글자로 세어지지 않도록 문자 하나를 1자로 센다 (DB의 글자 수 세는 방법과 맞춘다)

### 지역 코드와 동네 코드는 어디까지 검사하나

| 검사 | 지역 | 동네 | 버전 |
|---|---|---|---|
| 형식 (지역 숫자 5자리, 동네 숫자 10자리) | O | O | v0.2 / v0.4 |
| 지도 데이터에 있는 코드인지 | O | O | v0.2 / v0.4 |
| 동네가 그 지역에 속하는지 | - | O | v0.4 |
| 같은 동네가 두 번 들어왔는지 | - | O | v0.4 |

**지도 데이터에 있는지까지 검사하는 이유**
- 형식만 맞고 없는 지역 코드(예: `99999`)로 저장되면, 그 여행은 지도 어디에도 나오지 않는다
- 여행 목록은 지도에서 지역을 눌러야만 볼 수 있어서(F-02), 이런 여행은 **보이지도 않고 지울 수도 없다**
- 그래서 저장하기 전에 막는다

**검사 방법**
- 서버는 `public/data/`의 코드 목록 파일(모양 없이 코드와 이름만 담은 파일, TRD 6장)을 읽어 비교한다
- 동네가 그 지역에 속하는지는 코드 목록 파일에 적힌 소속(그 동네가 속한 시·군·구 코드)으로 확인한다
- 코드 목록 파일의 동네 부분은 v0.4에 들어온다. 그래서 v0.4 전에는 `dongCodes`가 `[]`가 아니면 `INVALID_DONG_CODE`로 막는다

**검사하지 않는 것**
- 지도 데이터가 나중에 바뀌어 이미 저장된 코드가 없어지는 경우는 API가 검사하지 않는다. DATA_MODEL.md 3장의 "지도 데이터를 바꿀 때의 규칙"으로 미리 막는다

## 6. 보안

- v2.0(로그인) 전에는 로그인 검사가 없다. 배포 주소를 알면 누구나 이 API로 여행을 보고, 고치고, 지울 수 있다. 그래서 연습용 기록만 넣는다
- 에러 응답에 DB 주소, 비밀번호, 서버 내부 오류 내용을 넣지 않는다

## 7. 앞 문서와 맞춘 것

- 저장 후 응답: 추가한 여행 하나만 돌려주고, 화면이 목록을 다시 받는 방식(3-2)으로 정했다. TRD 4장 11~12번을 이에 맞췄다
- 서버의 지도 데이터 읽기: 서버는 코드 검사를 위해 코드 목록 파일을 읽는다(5장). TRD 6장에 추가했다
